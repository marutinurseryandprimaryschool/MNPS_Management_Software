# CEO Plan: Principal Role, Fee Arrears Engine & Accounts Module
Generated by /plan-ceo-review on 2026-08-10 (rev 3 after two adversarial spec review iterations)
Branch: main | Mode: SELECTIVE EXPANSION
Repo: marutinurseryandprimaryschool/MNPS_Management_Software

## Context

Client (school) update request, three modules: (1) Principal-exclusive fee entry with
read-only teacher fee views, (2) month-to-month ECA arrears fix + pending-dues
auto-calculation across School/ECA/Van fees, (3) Principal-only income & expense
daily/monthly balance sheet.

### System audit facts that reshaped the spec
- Next.js 16 **static export** (`output: 'export'`) deployed on Netlify. **No server
  exists.** All writes go through the Firebase Web SDK from the browser; the ONLY
  enforcement surface is `firestore.rules`.
- The `principal` role **already exists** (src/types/enums.ts:5-12) and is treated as
  full admin by `isAdminLike()` in firestore.rules, Sidebar, BottomNav, and
  DashboardLayout. Work = narrow/specialize, not create.
- "Automated register syncing" needs no sync engine: one `feePayments` collection;
  central note / class register / teacher register are filtered views of it.
- ECA bug is structural: `extracurricular` is one annual number folded into
  `FeeStructureData.totalAmount` (AdminFees.tsx:143); no month dimension exists.
  Proven in-repo pattern to copy: bus fees (`busMonths[]` + `"Bus Fee - {month}"`
  payment categories + month grid at ParentFees.tsx:160-185).
- **Security holes:** `feePayments` and `expenses` are writable by ANY authenticated
  user, including anonymous parent sessions (firestore.rules:105-108, 159-162).
  Worse, `users` rules (firestore.rules:24-28) let any authenticated user create or
  write their own `users/{uid}` doc with an arbitrary role — a privilege-escalation
  path that would nullify any role-gated rule. Repo history already includes one
  parent-data-leak fix (460a203).
- Fee math is duplicated across six consumers (enumerated below) with divergent
  month lists (AdminFees: 12 calendar months; TeacherFees/ParentFees: 10 months
  June-March) and divergent scholarship handling (Teacher/Parent views and the
  year-end rollover ignore scholarships — live display bug + inflated carryover).
- Balance sheet is greenfield; `PaymentMode` (cash|upi|cheque|bank_transfer) exists
  on payments but is never aggregated; expenses lack a payment-mode field; recharts
  installed and unused; AdminReports is a placeholder.
- Teacher-student mapping exists: `teacherAssignments/{teacherId}_{year}` with
  `isClassTeacher` flag; TeacherFees currently loads ALL students/payments
  school-wide (unscoped).
- Pending staff `users` docs are **auto-ID** (`addDoc` via firestore-service.ts:62-74;
  call sites AdminSettings.tsx:232, AdminTeachers.tsx:176) and email-*queried* at
  first login (AuthContext.tsx:160-165). The "email-keyed" language in the current
  rules comments is a pre-existing misnomer. Firestore rules cannot run queries.

### The six fee-math consumers migrating onto the new engine
1. `AdminFees.tsx` (structures + payments + class drill-down)
2. `TeacherFees.tsx` (rewritten read-only, scoped)
3. `ParentFees.tsx` (month-wise arrears display, scholarship-corrected)
4. `AdminDashboard.tsx` ("Fee Collected" card)
5. `AdminReports.tsx` (total fee collected stat)
6. `AdminSettings.tsx` **Year-End Rollover** (carried-balance math at lines
   440-441 currently ignores scholarships/feeAdjustment and bus fees; it feeds
   `Student.previousBalance`, which this plan surfaces as the "Previous Balance"
   defaulter bucket — it must use the engine's scholarship-aware pending
   calculation or the bucket starts life inflated).

## Vision

### 10x Check
The school's entire money flow, legible at a glance. Sharmi Mam opens one screen
each morning: yesterday's collections, cash drawer vs bank balance, and who is
behind by how many months, per class. Every rupee traceable from a parent's hand to
the monthly balance sheet. Teachers stop being fee collectors and become fee
informers: their register is always current because it is the same record, not a
copy. Follow-ups happen from a defaulter list, not from memory. Paper artifacts
(balance sheet, defaulter list) print on demand for the correspondent/auditor.

### D10 trust-boundary note (explicit, so nobody over-trusts it)
User-management writes are narrowed to admin + correspondent (see item 3), matching
the capability map. Those two roles can therefore still technically self-assign
`principal` and reach the Accounts module. "Strictly Principal" is enforced against
teachers/parents at the rules level, and against admin/correspondent at the UI +
rules level **subject to the fact that role managers can self-promote**. Accepted
as an inherent limit of a single-school deployment with no backend; recorded here
so it is a known boundary, not an assumed guarantee.

## Accepted Scope (this plan)

1. **Shared fee engine** — new `src/lib/fee-utils.ts`: single canonical academic
   month list (June-March, capitalized labels matching existing payment-category
   strings; `MonthlyExam` enum values mapped via a label table), scholarship-aware
   effective fee, per-category arrears schedule:
   - ECA monthly slices, due after the month ends;
   - term due dates (a term with no due date is not yet due);
   - van fees per existing `busMonths` — the engine accepts ANY calendar month
     appearing in stored `busMonths` (including April/May), and a bus month is due
     after it ends, same rule as ECA;
   - `additionalFees[]` (arbitrary named charges in the structure): due
     immediately at year start (or admission month), shown as their own bucket;
   - FIFO allocation of historical lump-sum payments against monthly schedules.
   All six consumers above migrate onto it. Fixes parent/teacher scholarship
   display bug, rollover carryover math, and month-list divergence as part of the
   migration.
2. **Capability model** — new `src/lib/permissions.ts` mapping role → capabilities.
   Enumerated capability set: `canEnterFeePayments` (principal), `canEditFeePayments`
   (principal), `canManageFeeStructures` (admin, principal, correspondent),
   `canManageScholarships` (admin, principal, correspondent — scholarship
   configuration surfaces in the fees area, since the Principal is the fee person
   but does not hold `canManageSettings`), `canViewAllFees` (admin-like),
   `canViewOwnClassFees` (teacher), `canViewAccounts` (principal),
   `canAddExpenses` (principal), `canManageUsers` (admin, correspondent),
   `canManageSettings` (admin, correspondent). Replaces the duplicated role checks
   in DashboardLayout (x2), Sidebar, BottomNav, and SharedExpense's inline role
   list.
3. **Firestore rules redesign** — the linchpin of the whole plan:
   - **`users` collection (CRITICAL, fixes privilege escalation):**
     - Self-create: allowed only when `userId == request.auth.uid` AND
       `request.resource.data.role == 'parent'` (covers the anonymous parent flow
       at AuthContext.tsx:378-383).
     - Self-update: role immutable
       (`request.resource.data.role == resource.data.role`) for non-privileged
       writers.
     - **Staff first-login migration (rev 3 redesign — pending docs are auto-ID,
       rules cannot query):** AuthContext writes `migratedFrom: <pendingDocId>`
       into the new UID-keyed doc (it already holds the pending doc id at
       AuthContext.tsx:185). Rule permits create of `users/{uid}` with a
       privileged role only when `userId == request.auth.uid` AND
       `get(/databases/$(db)/documents/users/$(request.resource.data.migratedFrom))`
       satisfies: `.data.email == request.auth.token.email`,
       `.data.status == 'pending'`,
       `.data.role == request.resource.data.role`, AND
       `request.auth.token.email_verified == true` (defense-in-depth). Forged
       pending docs cannot escalate because self-create is parent-only. Batch
       `get()` sees pre-batch state, so the existing atomic swap works. No data
       migration or re-keying needed.
     - **Pending-doc consumption clause RETAINED (tightened from
       firestore.rules:32-34):** `allow delete: if isAuthenticated() &&
       resource.data.status == 'pending' && resource.data.email ==
       request.auth.token.email`. This is what lets the migration batch's
       delete half through; without it the atomic swap is denied on every staff
       first login and the silent `setDoc` fallback permanently reintroduces
       duplicate pending rows.
     - User-management writes (create/update/delete of OTHER users' docs):
       `role in ['admin','correspondent']` — matches the capability map;
       principal is excluded from user management in both UI and rules.
     - **First-user admin bootstrap (AuthContext.tsx:75-157) is denied by these
       rules.** Documented consequence: fresh installs seed the first admin doc
       via the Firebase console (or temporarily permissive bootstrap rules).
       Production already has users; the code path is retained but inert.
   - `isPrincipal()` helper; `feePayments`: `create/update` principal only,
     **`delete: if false`** (soft-delete via `deleted: true` update);
     `expenses`: read + write principal only.
   - `feePayments` **reads stay `isAuthenticated()`** — parents must read their
     child's payments and teachers their class's, and anonymous parent sessions
     cannot be scoped server-side (no custom claims possible without Admin SDK).
     Documented trust boundary: client-side filtering continues for payment reads.
   - Audit-trail subcollection `feePayments/{id}/history`: `read` principal only
     (explicit — a match block without a read rule default-denies and would break
     the Principal's own history view), `create` principal only,
     `update`/`delete: if false` (write-once). **Enforcement limit stated plainly:**
     rules cannot force an edit to be accompanied by a history entry (no
     cross-document invariants); the client writes payment-edit + history entry in
     a single `writeBatch` so the pair is atomic in practice; completeness beyond
     that is client convention, acceptable under the single-writer model.
   - New `accounts` collection (opening balances; reconciliation docs later):
     read/write principal only.
   - **Colliding admin tools (decided):** the AdminSettings "System Migration
     Tool" section that bulk-updates `feePayments` becomes unavailable to
     non-principal roles (UI-gated with an explanatory note); Master Reset's
     `feePayments` wipe is removed from the tool and documented as a
     Firebase-console operation (console bypasses rules). Both breakages are
     intentional consequences of `delete: if false` / principal-only writes.
   - (Follow-up security scope, documented not touched: any-auth WRITES on
     marks/attendance/chats etc., and any-auth READS on `users` — staff
     emails/phones are currently readable by anonymous parent sessions.)
4. **Schema additions** —
   - Fee structure: `ecaMonths: string[]` (default June-March) + term `dueDate`
     fields. Missing `dueDate` on an existing structure = term **not yet due**
     (defaulters invisible until Principal sets dates; the UI nudges her to set
     them). ECA slice = annual amount ÷ `ecaMonths.length`, rounded to the rupee,
     remainder added to the first month's slice.
   - Expense: `paymentMode: 'cash' | 'bank'` (required on new entries); historical
     expenses without the field default to **cash**.
   - `accounts/settings` doc: `openingCash`, `openingBank`, `openingAsOf` (date).
   - FeePayment: optional `deleted: boolean`; `models.ts` `FeeStructure` type
     updated to match the actual runtime shape (currently stale/aspirational).
5. **Principal dashboard & Accounts module** — new principal screens:
   - Income & Expense dashboard. Daily view: fee income by mode vs expenses by
     mode; **Cash in Hand = openingCash + Σ cash payments − Σ cash expenses, and
     Bank = openingBank + Σ (upi/cheque/bank_transfer) payments − Σ bank expenses,
     both summed strictly over transactions dated after `openingAsOf`.** Monthly
     view: aggregates of the same. All aggregates everywhere (dashboard cards,
     balance sheet, defaulter report, parent history) exclude `deleted: true`
     payments.
   - Expense entry (moved here, Principal-only).
   - Defaulter/arrears report (class-wise, month-wise, School/ECA/Van split,
     includes Previous-Balance and Additional-Fees buckets), printable.
   - PDF/Excel export for balance sheet + defaulter list.
   - **Fee-payment entry stays in the existing AdminFees payments UI**, gated by
     `canEnterFeePayments` (so only Principal sees/uses it); **payment edit +
     soft-delete + per-payment history view are net-new UI hosted in that same
     payments tab** (no edit/delete UI exists today). Fee-structures management in
     the same screen stays gated by `canManageFeeStructures` (admin, principal,
     correspondent). The split is capability-per-tab, not a new screen.
6. **Teacher read-only fee view** — TeacherFees rewritten: scoped to the teacher's
   class-teacher section only, read-only month-wise balances per student, no
   collect/entry UI; nav renamed from "Collect Fees" to "Fee Register". A teacher
   with no `isClassTeacher` assignment sees an explicit empty state ("You are not
   assigned as a class teacher this year"), not a blank page.
7. **Payment audit trail** — every edit or soft-delete of a feePayment writes a
   `history` entry (before-snapshot, actor, timestamp, action) in the same
   `writeBatch` as the payment mutation; deletes are soft (`deleted: true`),
   surfaced in Principal UI with history view.
8. **Parent view correctness** — ParentFees consumes the engine: correct
   scholarship-adjusted totals and month-wise ECA/term/bus arrears display.

## Key implementation decisions (resolved now, not during coding)
- **Users-rules redesign is a blocking prerequisite** for every principal-only
  guarantee (see scope item 3). Ship order within the change: users rules → money
  rules → UI.
- Historical "Extracurricular" lump payments allocate FIFO (oldest unpaid month
  first) against the monthly schedule. Pure display-layer allocation in the engine;
  no data rewrite, no recategorization script, history stays untouched.
- New ECA payments are recorded month-tagged (`"ECA - {month}"`, capitalized month
  labels, same convention as `"Bus Fee - {month}"`); the legacy `"Extracurricular"`
  category remains readable for history and feeds the FIFO allocator.
- Current month is NOT due until it ends (client's example is authoritative), for
  ECA and bus months alike.
- **Scholarship / `feeAdjustment` flat overrides pro-rate across the standard
  schedule shape**: scale factor = override ÷ standard total (terms + ECA +
  additionalFees — everything in the override's replacement basis), applied to
  every term, ECA month slice, and additional-fee bucket, so scaled buckets sum
  exactly to the override. When the standard total is 0, the factor is 1 (nothing
  due, no division). A scholarship student appears in the defaulter report with
  proportionally scaled dues (never as a full-fee defaulter). Van fees are NOT
  scaled (transport is charged as-is; matches current `effectiveClassFee` behavior
  where bus fee is added outside the override).
- `Student.previousBalance` (prior-year dues) joins pending dues as a separate
  "Previous Balance" bucket: due immediately, not month-allocated, listed first in
  the defaulter report and payable as its own category (`"Previous Balance"`).
  The year-end rollover that POPULATES it becomes engine consumer #6 so the
  carried number is scholarship- and bus-aware.
- Mid-year admissions: dues start from the student's admission month (fallback:
  academic year start when admission date is absent).
- Deploy ordering: app deploy first, rules deploy immediately after. Brief window
  where stale clients retain old (looser) write behavior — acceptable. After the
  rules land, stale clients (old AuthContext without `migratedFrom`) fail staff
  FIRST-LOGIN migration until refreshed; self-healing on reload, noted for the
  deploy checklist.
